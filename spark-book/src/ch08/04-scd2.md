## Table design

| customer_id | name | city | tier | row_hash | valid_from | valid_to | is_current |
|---|---|---|---|---|---|---|---|
| 1 | Alice | Kyiv | gold | … | 2026-10-01 | 9999-12-31 | true |

Three design decisions, each with a reason:

- **`valid_from`**: the date this version became true. **Business time**, not load time, if the
  source gives you one (the capstone does).
- **`valid_to`**: the date it stopped being true, **exclusive**. A version valid `[10-01, 10-05)`
  hands over to the next one at exactly `10-05`, with no gaps and no overlaps, and
  `date >= valid_from AND date < valid_to` picks exactly one version for any date.
  The current version gets a far-future date, `9999-12-31`, instead of `NULL`, so that same range
  condition works without `OR valid_to IS NULL`.
- **`is_current`**: redundant with `valid_to = 9999-12-31`, but it makes "current state" queries
  trivial and is a natural filter in the MERGE condition.

## The problem: one source row, two actions

For a *changed* customer, the MERGE has to do **two** things: expire the current row (UPDATE) **and**
insert the new version (INSERT). But in a MERGE, each source row triggers **at most one** clause.

## The trick: send changed customers twice

Build a **staged** source in which every changed customer appears twice. One copy is keyed normally,
and the other has `merge_key = NULL`, so it can never match anything.

Day 2's staged source and what the MERGE does with each row:

| source row | `merge_key` | matches a current row? | clause that fires | effect |
|---|---|---|---|---|
| Alice (Dnipro), copy 1 | `1` | ✅ Alice/Kyiv, hash differs | `whenMatchedUpdate` | Kyiv row: `is_current = false`, `valid_to = 10-05` |
| Alice (Dnipro), copy 2 | `NULL` | ❌ never | `whenNotMatchedInsert` | new row Dnipro, `[10-05, 9999-12-31)` |
| Bob (gold), copy 1 | `2` | ✅ hash differs | `whenMatchedUpdate` | silver row expired |
| Bob (gold), copy 2 | `NULL` | ❌ | `whenNotMatchedInsert` | new row gold |
| Carol (unchanged) | `3` | ✅ but hash **equal** | none | nothing: no rewrite, no fake version |
| Dan (new) | `4` | ❌ no row for 4 | `whenNotMatchedInsert` | first version of Dan |

Result: 3 + 3 = **6 rows**, 4 of them current.

   - `whenMatchedUpdate(condition="t.row_hash <> s.row_hash", set={is_current: false, valid_to: s.eff})`
   - `whenNotMatchedInsert(values={...})`: a new row with `valid_from = s.eff`,
     `valid_to = 9999-12-31`, `is_current = true`.

**Pause: why `AND t.is_current = true` in the merge condition?** <span class="tag">2 min</span>

Think about day 3: Alice already has two rows, and only one of them is current.

<details>
<summary>Answer</summary>

Without it, Alice's keyed copy matches **both** of her rows: the expired Kyiv row from day 1 *and* the
current Dnipro row. Any expired row whose hash differs from the incoming one would then fire
`whenMatchedUpdate` too, and its `valid_to` would be **overwritten** with the new date. Closed
intervals would stretch and overlap, and history would be silently destroyed. On day 3 you might not
even notice: Alice's expired day-1 row has the *same* hash as the new Kyiv version, so it happens to
be left alone. That's exactly the kind of bug that passes a test and breaks in production.

The condition limits every match to the one row that may still change, the current version.
**History rows are immutable.**
