# Slowly Changing Dimensions (SCD) with Delta MERGE

A **dimension** describes entities (customers, products, airports — remember `airport_states`
from 2-02). Its attributes change *slowly*: a customer moves city, gets a new tier.
The question SCD answers: **what do we do with the old value?**

| Type | Strategy | History? | Typical use |
|---|---|---|---|
| **0** | never change after insert | — | birth date, original signup channel |
| **1** | overwrite | ❌ none | fixing typos, attributes nobody analyses historically |
| **2** | close the old row, insert a new one (`valid_from`/`valid_to`/`is_current`) | ✅ full | reporting "as it was at the time" — **the important one** |
| **3** | extra column with the previous value | ⚠️ one step | "current vs previous region" comparisons |
| **4** | current table (Type 1) + separate history table | ✅ full, separate | huge dims where most queries need only current |
| **6** | 1+2+3 hybrid: SCD2 rows + a "current value" column on every row | ✅ | report by both historical and current value |

Today: Types 1, 2 (deep), 3. Type 4 = Type 1 table + Change Data Feed from 1-08 as history.

Solutions: `1-09-scd-solutions.md`. Every task ends with `assert`s → ✅ when done.

```python
], schema)

D1, D2, D3 = "2026-10-01", "2026-10-05", "2026-10-10"

TRACKED = ["name", "city", "tier"]


def add_hash(df):
    """One hash over the tracked attributes = cheap 'did anything change?' check.

    Why coalesce: concat_ws SKIPS nulls, so ('a', null) and (null, 'a') would both give 'a'
    and hash the same. Replacing null with a marker keeps them different.
    """
    parts = [sf.coalesce(sf.col(c).cast("string"), sf.lit("<null>")) for c in TRACKED]
    return df.withColumn("row_hash", sf.sha2(sf.concat_ws("||", *parts), 256))


def last_merge_metrics(path):
    """operationMetrics of the latest commit: numTargetRowsUpdated, numTargetRowsInserted, ..."""
    return DeltaTable.forPath(spark, path).history(1).first()["operationMetrics"]
```

## Task 1 — SCD Type 1 (overwrite, no history)

Write `scd1_merge(updates, path)`:
- add `row_hash` with `add_hash`
- if the table doesn't exist yet (`DeltaTable.isDeltaTable(spark, path)`) → just write it
- otherwise MERGE on `customer_id`:
  - matched **and the hash differs** → `whenMatchedUpdateAll(condition=...)`
  - not matched → `whenNotMatchedInsertAll()`

Why the hash condition? Without it, Carol (sent again, unchanged) would be *rewritten* anyway:
more files touched, a fake "update" in the history and in the Change Data Feed.

## Task 3 — SCD Type 2 MERGE (the staged-union trick)

**The problem:** for a *changed* customer we need **two** actions — expire the current row
(UPDATE) **and** insert the new version (INSERT). But in a MERGE each source row triggers at
most **one** action.

**The trick:** send changed customers into the MERGE **twice**:

| source row | `merge_key` | matches current row? | action |
|---|---|---|---|
| changed customer, copy 1 | `customer_id` | ✅ | `whenMatchedUpdate` → `is_current=false`, `valid_to=eff` |
| changed customer, copy 2 | `NULL` | ❌ never (NULL ≠ anything) | `whenNotMatchedInsert` → new current version |
| new customer | `customer_id` | ❌ | `whenNotMatchedInsert` |
| unchanged customer | `customer_id` | ✅ but hash equal | nothing |

Write `scd2_merge(updates, path, effective_date)`:
1. `updates` = `add_hash(updates)` + column `eff` = effective date
2. `current` = target rows with `is_current = true`
3. `changed` = `updates` joined to `current` on `customer_id` where hashes differ,
   selecting `NULL AS merge_key` (`sf.lit(None).cast("bigint")`) + all `updates` columns
   (use aliases `u`/`c` and `sf.col("u.<col>")`, otherwise `customer_id` is ambiguous)
4. `staged` = `updates` with `customer_id AS merge_key` + all columns, `unionByName(changed)`
5. MERGE `staged` into the target on `t.customer_id = s.merge_key AND t.is_current = true`
   - `whenMatchedUpdate(condition="t.row_hash <> s.row_hash", set={is_current: false, valid_to: s.eff})`
   - `whenNotMatchedInsert(values={...})` — new row with `valid_from = s.eff`,
     `valid_to = 9999-12-31`, `is_current = true`

Think: why is `AND t.is_current = true` in the merge condition? What would go wrong without it
on day 3 (Alice already has 2 rows)?

`o.customer_id = d.customer_id AND o.order_date >= d.valid_from AND o.order_date < d.valid_to`
(this is a *range join* — note why `valid_to` is exclusive and why `9999-12-31` is handy).
